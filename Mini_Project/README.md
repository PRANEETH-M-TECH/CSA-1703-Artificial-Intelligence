## 1. Quick start (single command)

There's a root-level `package.json` that wraps both the backend and frontend so you never have to juggle two terminals by hand.

### One-time setup

```bash
npm run setup
```
This creates the backend's Python virtual environment, installs backend dependencies (`pip install -r backend/requirements.txt`), and installs frontend dependencies (`npm install` in `frontend/`) — one command, run once.

### Development — one command, two servers, live-reload

```bash
npm run dev
```
This uses [`concurrently`](https://www.npmjs.com/package/concurrently) to start **both** the FastAPI backend (port 8000, auto-reload) and the Vite frontend (port 5173, hot-reload) in a single terminal, with color-coded `[backend]` / `[frontend]` log prefixes so you can tell which process printed what. Open **`http://localhost:5173`**.

This is still *two processes* under the hood (a browser dev server and an API server are different things by nature), but it is genuinely **one command** to start and **one command** (`Ctrl+C`) to stop both — that's what solves the "two terminals" friction.

### Production / deployment — truly one process, one port

```bash
npm run prod
```
This does two things in sequence:
1. `npm run build` — compiles the React app into static files (`frontend/dist/`).
2. `npm run start` — starts **only** the FastAPI backend, which detects that `frontend/dist/` exists and serves the built React app directly (see the static-file mount at the bottom of `backend/app/main.py`). The API (`/api/*`) and the entire UI are now served by **one Python process on one port** (`http://localhost:8000`).

This is the deployment-ready mode: push this one process to a host (Render, Railway, an EC2/VM, a Docker container, etc.) and there's nothing else to run or coordinate — no separate static hosting, no reverse proxy required to stitch frontend and backend together (though you can still put one in front for TLS/scaling).

| Command | What it does | Use for |
|---|---|---|
| `npm run setup` | Install everything (once) | First-time setup |
| `npm run dev` | Backend (reload) + frontend (HMR), one terminal | Day-to-day development |
| `npm run build` | Compile the React app to `frontend/dist/` | CI / pre-deploy step |
| `npm run start` | Run only the backend, serving `frontend/dist/` if present | After a build, or in production |
| `npm run prod` | `build` then `start` | Full deploy in one shot |

Interactive API documentation (auto-generated by FastAPI) is always available at **`http://localhost:8000/docs`** — useful for demoing individual endpoints to an examiner without going through the UI.

### Demo login

```
email:    demo@taskmind.app
password: demo1234
```

Prefilled on the Login screen — just press "Sign in". On first backend startup this account is auto-seeded with 11 realistic tasks (including one deliberately overdue task, to show Module 2 firing immediately) and 60 synthetic history records (to show Module 3's dashboards populated immediately). See `backend/app/seed.py`.

You can also create a brand-new account from Signup — it starts empty, which is useful for demonstrating the "cold start" behavior described in §5.

### Resetting all data

```bash
# stop the backend first, then:
del backend\taskmind.db        # macOS/Linux: rm backend/taskmind.db
```
Restart the backend and the demo account + seed data are recreated automatically.

## 2. Database

**Engine:** SQLite — a single file, `backend/taskmind.db`, created automatically the first time the backend starts (no separate database server to install or run). Accessed through **SQLAlchemy** as the ORM (`backend/app/database.py`).

Every user's data — their own tasks, generated schedule, detected conflicts, and completion history — is isolated by `owner_id`, so multiple accounts can safely share the same database file.

**Tables** (`backend/app/models/`):

| Table | Purpose | Key columns |
|---|---|---|
| `users` | One row per account | `email`, `hashed_password` (bcrypt), `work_start_hour`, `work_end_hour` |
| `tasks` | Everything the user asked to get done | `title`, `category`, `deadline`, `duration_minutes`, `priority`, `status` (`pending`/`scheduled`/`completed`) |
| `schedule_entries` | Module 1's output — one row per task placed into a time slot | `task_id`, `start_time`, `end_time`, `slack_minutes` |
| `conflicts` | Module 2's output — one row per detected conflict | `conflict_type`, `task_a_id`, `task_b_id`, `description`, `suggestion`, `rule_trace` (the stored forward-chaining derivation, replayed for backward-chaining explanations), `resolved` |
| `history_records` | Module 3's training data — one row per completed task | `task_type`, `time_of_day`, `planned_duration`, `actual_duration`, `completed_on_time` |

Why SQLite: zero setup for a semester-scale project (no server process, no credentials, works identically on every machine), while still being a real relational database accessed through a real ORM — the exact same SQLAlchemy models would work against PostgreSQL by changing one connection string in `database.py`, which is worth mentioning if an examiner asks "what if this had to scale?"

## 3. First-time walkthrough — what to actually click

You just logged in (with the demo account or a fresh signup) and you're on the **Home Dashboard**. Here's the actual order of operations to see the whole app work, and exactly what each step demonstrates:

1. **Look at Home.** The "Module summary" panel on the right explicitly labels **Module 1 · Scheduler**, **Module 2 · Reasoning**, **Module 3 · Learning** with a live stat under each — this is the on-screen map of which module does what, always visible, so you're never guessing which part of the app corresponds to which AI technique.
2. **Add a task** — tap the **+** floating button (Home or Tasks tab). Fill in a title, category, deadline, duration, priority. This is raw input; nothing AI-related happens yet, it's just data entry into the `tasks` table.
3. **Go to the Schedule tab and press "Generate schedule."** *This* is the first AI action: it calls Module 1 (CSP + A* search) to place every pending task into a time slot. You'll see a summary line naming the algorithm and how many tasks it placed.
4. **If a badge/banner appears mentioning a conflict**, that's Module 2 — it runs automatically right after every schedule generation. Tap **Conflict Alerts** to see the list, then tap a conflict to expand it: the accordion trace ("R1: ... R2: ...") is Module 2's *backward chaining* explaining, rule by rule, exactly why that conflict was flagged.
5. **Tap "Open resolution"** on a conflict and pick reschedule / shorten / drop. This mutates the task so the *next* "Generate schedule" run places it without conflict — closing the loop back to step 3.
6. **Go back to Tasks and swipe a task right (or tap Complete).** This logs a completion record — the raw material for Module 3.
7. **Go to the Insights tab.** The charts (completion rate by category, productivity by time-of-day) and the "Model accuracy" stat are Module 3 — a real decision tree trained on every completion record in the database, retrained fresh each time you open this screen.
8. **Tap "Recommendations."** Same trained model, used differently: for each task category it scans hours of the day and surfaces the one with the highest predicted on-time probability, as a swipeable card.
9. **Profile tab** lets you change your daily work-hour window — this directly changes Module 1's constraint domain, so try generating a schedule again after narrowing your hours and see how placements shift.

That's the entire app: **add tasks → generate (Module 1) → see & resolve conflicts (Module 2) → complete tasks → see insights & recommendations (Module 3) → repeat.**

## 4. Application flow — what happens when you use it

This is the concrete, screen-by-screen path through the app, and which backend call fires at each step.

```
Splash (checks saved JWT)
  │
  ├─ no token, first visit ──▶ Onboarding (3 slides) ──▶ Login
  ├─ no token, returning ────▶ Login ──▶ Signup (if new)
  └─ valid token ────────────▶ Home Dashboard
                                   │
        ┌──────────────────────────┼───────────────────────────┐
        ▼                          ▼                            ▼
   Task List                 Schedule View                 Insights
  (add/edit/delete/       "Generate schedule" button     (Recharts, decision
   complete tasks)          → runs Module 1 (A*/CSP)        tree predictions)
        │                          │                            │
        │                          ▼                            ▼
        │                   Conflicts detected?           Recommendations
        │                   → runs Module 2                (swipeable cards)
        │                   (forward chaining)
        │                          │
        │                          ▼
        │                   Conflict Alerts screen
        │                   (tap to expand → Module 2
        │                    backward chaining explains it)
        │                          │
        │                          ▼
        │                   Conflict Resolution
        │                   (reschedule / shorten / drop)
        │                          │
        └────────── task marked "completed" ──────────┐
                                                        ▼
                                          POST /history → feeds
                                          Module 3's training data
```

Step by step, in the order a first-time user actually experiences it:

1. **Sign up / log in.** The backend issues a JWT (`python-jose`), stored in `localStorage`; every subsequent request carries it in the `Authorization` header (`frontend/src/api/client.js`).
2. **Add tasks** (Task List → "+" → Add Task sheet). Each task has a title, category, deadline, estimated duration, and priority — this is exactly the CSP variable definition Module 1 will consume.
3. **Generate schedule** (Schedule tab → "Generate schedule" button). This calls `POST /api/schedule/generate`, which runs **Module 1** (CSP + A* search, detailed in §5) and writes the resulting time slots to the database.
4. Immediately after generating, the frontend calls `POST /api/conflicts/check`, which runs **Module 2** (forward chaining over the just-generated schedule) and stores any detected conflicts.
5. If conflicts exist, a badge appears on Home and Schedule. Opening **Conflict Alerts** and tapping a conflict calls `GET /api/conflicts/{id}/explain`, which runs **Module 2's backward chaining** to produce the human-readable derivation trace shown in the accordion.
6. From there, **Conflict Resolution** lets the user pick reschedule / shorten / drop, which calls `POST /api/conflicts/{id}/resolve` — this mutates the task (e.g. shrinks its duration) so the *next* schedule generation naturally fits it in.
7. **Completing a task** (swipe right on Task List, or the Complete button) calls `POST /api/history`, logging `(category, hour-of-day, planned vs actual duration, on-time?)`. This is the raw data **Module 3** trains on.
8. **Insights** and **Recommendations** call `GET /api/insights` and `GET /api/recommendations`. Both endpoints retrain a fresh `DecisionTreeClassifier` (Module 3) from all of the user's history records on every call — cheap enough at this data scale to skip a separate "stale model" cache — and return predictions.
9. **Profile** lets the user change their daily work-hour window (`work_start_hour` / `work_end_hour` on the `User` model), which directly changes Module 1's CSP domain on the next schedule generation.

This is the agent's **perceive → reason → act → learn** loop: Module 1 *acts* (proposes a schedule) from what it *perceives* (tasks + constraints); Module 2 *reasons* about that proposal and explains problems; completed/failed outcomes are *learned* from by Module 3, which feeds back into future scheduling decisions (better duration/likelihood estimates, better recommended time-of-day).

## 5. Module deep-dive (design + when each one runs)

### Module 1 — Intelligent Scheduling Engine
**File:** [`backend/app/services/scheduler.py`](backend/app/services/scheduler.py) · **Syllabus:** Unit I (agents, problem formulation), Unit II (informed search, A*, CSP)

**When it's triggered:** only when the user explicitly presses **"Generate schedule"** on the Schedule screen (`POST /api/schedule/generate`). It is never run silently in the background — scheduling is a deliberate, visible agent action, which is also why the loading state ("Generating...") and the summary line ("Module 1 placed N task(s)...") are shown after it runs.

**How it's designed, step by step:**
1. **Problem formulation as a CSP:**
   - *Variables* = every pending task (not yet completed).
   - *Domain* = candidate start-time slots, generated at 15-minute granularity, inside the user's work-hour window (`work_start_hour`–`work_end_hour`), over a 21-day planning horizon (`_candidate_slots`).
   - *Constraints*: (a) **no-overlap** with any slot already placed in this run, (b) **work-hours** — a task's full duration must fit inside the window, (c) **no-past** — a slot can't start before "now".
   - The deadline is treated as a **soft constraint**: violating it doesn't eliminate a slot, it just costs "lateness minutes", which the search tries to minimize.
2. **Variable ordering (most-constrained-first heuristic):** tasks are sorted by **earliest deadline, then highest priority** before scheduling begins (`ordered = sorted(tasks, key=lambda t: (t.deadline, -t.priority))`). This is a classic CSP variable-ordering heuristic adapted for scheduling — tasks with the least slack are committed first, before easier tasks eat up good slots.
3. **A\* search per task:** for each task, every valid candidate slot is pushed onto a min-heap priority queue with:
   - `g(slot) = lateness_minutes(slot)` — the actual cost incurred if this slot is chosen (0 if it meets the deadline).
   - `h(slot) = minutes_from_now(slot) × 1e-6` — a tiny admissible heuristic that only breaks ties between equally-lateness slots, nudging the search toward the earliest (highest-slack) option.
   - `f = g + h`. The heap pop order is exactly A*'s expansion order, so the **first feasible slot popped is optimal** for that task given everything committed so far.
4. Once a task is placed, its slot is added to the `occupied` list so later tasks' overlap constraint accounts for it — this greedy-committal-per-variable approach is what keeps the search tractable (no combinatorial backtracking across all tasks at once), which is an intentional, explainable trade-off for a capstone-scale system.
5. Tasks that have no feasible slot before the search bound are returned as `unscheduled_task_ids` and surfaced in the UI.

**Output:** an ordered list of `(task, start_time, end_time, slack_minutes)` — written to the `ScheduleEntry` table and returned to the frontend for the calendar view.

> **If asked "why A\* and not plain greedy?"** — plain greedy-best-first would only use `h` and ignore actual incurred cost, so it could pick a slot that "looks close" but causes large lateness. A\* combines the real cost so far (`g`) with the heuristic (`h`), which is what guarantees the slot chosen for each task is provably optimal for that task under the constraints already committed.

### Module 2 — Reasoning & Conflict Resolution
**File:** [`backend/app/services/rules_engine.py`](backend/app/services/rules_engine.py) · **Syllabus:** Unit III (propositional/FOL, forward & backward chaining)

**When it's triggered:**
- **Forward chaining** runs automatically right after every schedule generation (the frontend calls `POST /api/conflicts/check` immediately after `POST /api/schedule/generate`), and can also be re-run manually by revisiting the Schedule/Conflicts screen.
- **Backward chaining** runs **on demand, per conflict**, only when the user taps a conflict card to expand it (`GET /api/conflicts/{id}/explain`) — it is not computed for conflicts the user never opens, mirroring how backward chaining is meant to be *goal-directed* (start from "why is X true?" rather than deriving everything eagerly).

**How it's designed:**
1. **Facts** are derived live from the current database state: every `ScheduleEntry` (start/end time, task, category, priority) and every `Task` (deadline, status).
2. **Rule base** (small and explicit on purpose, so it's easy to defend in a viva) — 8 rules, `R1`–`R8`:
   - `R1`: `IF task_A.time overlaps task_B.time THEN conflict(A, B)`
   - `R2`–`R4`: priority-based resolution — reschedule whichever of the two overlapping tasks has *lower* priority (`R2`/`R3`); if priorities tie, reschedule whichever was placed later (`R4`).
   - `R5`: `IF task.deadline < now AND task.status != completed THEN overdue(task)`
   - `R6`: `IF overdue(task) THEN suggest(immediate action)`
   - `R7`: `IF scheduled_end(task) > deadline(task) THEN conflict_deadline_overrun(task)` — catches the case where Module 1 *had* to place a task after its own deadline because no earlier slot existed.
   - `R8`: `IF conflict_deadline_overrun(task) THEN suggest(shorten or reschedule earlier)`
3. **Forward chaining** (`forward_chain()`): every rule is evaluated against the current facts in one pass (overlap checks are pairwise across all scheduled entries; overdue/deadline-overrun checks are per-task) — this is a direct, small-scale forward chaining pass rather than a general-purpose inference loop, which is appropriate given the rule base is finite and non-recursive (no rule's conclusion feeds back in as another rule's premise). Every match produces a `Conflict` row, stored with **the exact trace of which rule fired and why** (`rule_trace`, JSON-encoded).
4. **Backward chaining** (`backward_chain_explain()`): given a specific conflict (the *goal*), it retrieves the stored derivation trace — i.e. it reconstructs the chain "which rule's consequent matches this goal, and were its premises satisfied?" — and returns it as ordered, human-readable steps for the accordion UI. If the raw trace is ever unavailable, it falls back to re-deriving the explanation directly from current facts.
5. **Resolution** (`POST /api/conflicts/{id}/resolve`): applies the user's chosen action (reschedule / shorten duration by ~40% / drop the slot) directly to the `Task` row, so the *next* Module 1 run naturally produces a conflict-free placement.

> **If asked "why not a general Prolog-style resolution engine?"** — the design document intentionally scopes this to a small, hand-written rule set (10–15 rules) specifically so forward/backward chaining can be demonstrated clearly without needing a full FOL theorem prover — the mechanism (chaining over explicit premises/conclusions) is the same principle at smaller, explainable scale.

### Module 3 — Adaptive Learning & Personalization
**File:** [`backend/app/services/ml_model.py`](backend/app/services/ml_model.py) · **Syllabus:** Unit IV (inductive learning, decision trees, statistical learning)

**When it's triggered:**
- Every time a task is marked complete, `POST /api/history` logs a new training row (task category, hour-of-day it was scheduled for, planned vs. actual duration, whether it finished on time).
- The model is **retrained fresh on every call** to `GET /api/insights`, `GET /api/recommendations`, or the explicit `POST /api/model/train` — there's no persisted/stale model object; at this data scale (tens–hundreds of rows per user) retraining a depth-4 decision tree takes milliseconds, so "always retrain" is simpler and always up-to-date rather than adding cache-invalidation complexity.
- Needs **at least 6 history rows** to train at all (`MIN_ROWS_TO_TRAIN`); below that, `/recommendations` returns an empty list and `/insights` reports `model_accuracy: null` — this is a deliberate, visible "cold start" state rather than a silent failure.

**How it's designed:**
1. **Features → label:** `(task_category [label-encoded], time_of_day [0–23], planned_duration_minutes) → completed_on_time [0/1]`.
2. **Model:** `sklearn.tree.DecisionTreeClassifier(max_depth=4)` — depth is capped both to avoid overfitting on small per-user datasets and to keep the tree shallow enough to explain in a viva ("it's asking: was this a Study task, scheduled early or late, for how long?").
3. **Train/validate:** if ≥10 rows and both classes present, an 80/25 `train_test_split` gives a held-out accuracy score (shown on the Insights dashboard as "Model accuracy"); the model is then refit on the full dataset for production use. Below that threshold, it just fits on everything (too little data to hold out a meaningful test split).
4. **Recommendations** (`recommend_best_hours()`): for every category the user has history in, the trained tree's `predict_proba` is swept across hours 6–22 to find the hour with the **highest predicted probability of on-time completion** — this is literally "ask the model: at what hour is this category most likely to succeed?" and surface the top answer as a card, e.g. *"You complete 'Fitness' tasks on time 100% of the time when scheduled around 6AM."*
5. **Insights** (`/api/insights`) additionally computes plain descriptive statistics (completion rate, overdue count, per-category and per-hour on-time percentages) directly from the history table — these are shown alongside the model's accuracy so the dashboard mixes simple statistics with the learned model's own self-assessment.
6. **Feedback into Module 1:** the design intends these predictions to also improve future duration/likelihood estimates fed back into the scheduler — in this implementation that loop is expressed as the recommendation surfaced to the *user*, who can then adjust a task's duration/priority/deadline themselves before the next `Generate schedule` run (a human-in-the-loop version of the same feedback path).

> **If asked "why a decision tree and not something else?"** — it's directly specified by the design document, it's fast to train on small per-user datasets with no GPU/infra needs, and — critically for a viva — it's interpretable: you can literally print `export_text(clf)` and read the exact splits the model is making, unlike a black-box model.

## 11. Viva / faculty Q&A cheat sheet

Quick answers to the questions most likely to come up:

- **"Show me the search algorithm running."** Add a task with a near-term deadline that overlaps another task's slot, press "Generate schedule" on the Schedule screen, and point to the summary line naming the algorithm and slot count. Then open `backend/app/services/scheduler.py:_a_star_best_slot` to show the priority queue.
- **"Show me forward chaining."** After generating a schedule with an overlapping/overdue task, open Conflict Alerts — the list itself *is* the output of one forward-chaining pass (`forward_chain()`).
- **"Show me backward chaining."** Tap a conflict card to expand it — the accordion trace (`R1: ... R2: ...`) is the backward-chained derivation for that specific conflict, fetched live from `GET /conflicts/{id}/explain`.
- **"Show me the learning."** Open Insights — "Model accuracy" is a real held-out test score from `DecisionTreeClassifier`; Recommendations are the same model's `predict_proba` swept across hours.
- **"What's the agent loop?"** Module 1 acts → Module 2 reasons about the action and explains problems → completed/failed task outcomes are logged → Module 3 learns from them → its recommendations inform how the user (or a future automated version) adjusts tasks before the next Module 1 run. See §4 diagram.
- **"Where's the CSP?"** Variables = tasks, domain = 15-minute slots inside work hours, constraints = no-overlap / work-hours / no-past, in `_candidate_slots()` and the constraint check inside `_a_star_best_slot()`.
